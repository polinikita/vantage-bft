# docker-bench

A docker-based **distributed** local benchmark for vantage: one container per
validator, WAN latencies injected at the transport level with real `tc netem` (not the
in-process `LatencyTable` simulation `node local-benchmark` uses), and a link-disruption
script for blips (drop / reset). Complements, and is independent of, `node
local-benchmark` (single-process, in-process latency) and `benchmark/` / `fab`
(multi-instance AWS deployment) -- this tool sits in between: a distributed, real-TCP,
real-tc-shaped run, but entirely on one docker host.

Nothing under `docker-bench/` changes protocol behavior. It reuses the repository's
shared monitoring stack and dashboard. See "Client" below for why the planned `node
client` subcommand addition was not needed after all.

## Layout

```
docker-bench/
  Dockerfile        multi-stage build (see "Caching design")
  gen.py            generates keys/committee.json/parameters.json/tc scripts/docker-compose.yml
  entrypoint.sh     baked into the image: applies tc, runs primary+worker+client, supervises
  blip.sh           host-side link-disruption orchestrator (drop|cut, `docker exec` + iptables)
  results.py        scrapes every container's Prometheus endpoint, prints TPS/latency/timeline
  run.sh            end-to-end: gen -> build -> up + dashboard -> wait -> run -> down validators
  monitoring-compose.yml attaches shared Prometheus to the private validator network
  data/             generated by gen.py every run (gitignored): keys, committee/parameters,
                    Prometheus targets, per-node tc scripts, manifest.json, logs, RocksDB stores
  docker-compose.yml generated by gen.py (gitignored)
```

## Quick start

```
cd docker-bench
./run.sh --nodes 4 --rate 200 --duration 60 --protocol vantage
```

This generates the config, builds the image, brings up 4 containers on a private
`172.28.0.0/16` bridge network, waits for them to come up, prints a live
`TIMELINE: sec=... committed_total=... committed_delta=...` line once per second for
60s (the same format `node local-benchmark --timeline` uses), prints a final summary,
then tears the validator stack down. It also starts the shared Prometheus/Grafana
monitoring stack and prints the direct dashboard URL:

```
http://localhost:3003/d/vantage-local-benchmark
```

The dashboard includes committed TPS, ordering and materialized transaction latency,
CPU, and resident memory per validator, plus all protocol/network metrics. Prometheus
scrapes one primary and one worker process per validator through the private Docker
network. Monitoring remains up after the validators stop so the completed run stays
inspectable. Its named TSDB volume keeps a rolling 24 hours of samples across runs
and Prometheus automatically prunes older data. Stop monitoring when finished with:

```
docker compose -f ../monitoring/docker-compose.yml down
```

That command preserves the 24-hour metrics volume. Add `-v` to delete the complete
metrics history immediately.

While a run is in flight (from another terminal):

```
docker-bench/blip.sh 0 1 5 drop      # node 0 <-> node 1 unreachable for 5s (pause semantics)
docker-bench/blip.sh 2 all 10 cut    # isolate node 2 from everyone for 10s (reset semantics)
```

To drive the steps individually instead of `run.sh`:

```
python3 gen.py --nodes 4 --rate 200 --duration 60 --protocol vantage
DOCKER_BUILDKIT=1 docker build -f Dockerfile -t vantage-docker-bench:latest ..
docker compose -f docker-compose.yml up -d
python3 results.py --watch --duration 60   # live timeline + a self-baselined TPS summary
python3 results.py                          # point-in-time snapshot only (no rate -- see "Results")
docker compose -f docker-compose.yml down
```

`--nodes`/`--rate`/`--duration`/`--protocol` are handled by both `run.sh` and `gen.py`;
every other `gen.py` flag (`--tx-size`, `--mode`, `--no-latency`, `--withhold[-at|-for]`,
`--delta-ms`, `--max-batch-delay-ms`, `--max-header-delay-ms`, `--all-to-all`,
`--no-ack-watermarks`, `--ack-watermark-period-ms`, `--no-digest-statements`, `--no-batch-messages`,
`--batch-max-bytes`, `--batch-max-delay-ms`) passes straight through `run.sh` to
`gen.py` and from there into `parameters.json` -- see `python3 gen.py --help`. These
mirror `node local-benchmark`'s own flag names/semantics one-for-one (they set the same
`config::Parameters` fields).

Constraints inherited from the owner: never run more than one 20-node cluster
(`gen.py` enforces `--nodes <= 20`); keep local dev runs at `--nodes 4`.

## Caching design (owner requirement)

The build stage combines two independent caching mechanisms, both required and both
load-bearing (this repo has no `cargo-chef` dependency; the same effect is achieved by
hand with plain `--mount=type=cache` and a stub-source layer). Both of the nuances
below were found the hard way, empirically, while developing this Dockerfile -- not
anticipated up front -- so they're documented in the Dockerfile itself, not just here.

1. **BuildKit cache mounts** on the cargo registry, the cargo git checkout cache, and
   the shared cargo **workspace** `target/` directory. These live in BuildKit's own
   persistent cache store, independent of Docker's image-layer cache -- they survive
   even when an upstream `COPY` layer is invalidated and its dependent `RUN` has to
   re-execute, so a plain incremental `cargo build` inside that `RUN` still only
   recompiles what actually changed.
2. **A dependency-precompile layer.** Only the 9 `Cargo.toml` files are copied first; a
   trivial one-line stub `src/lib.rs` (per library crate) / `fn main() {}` (per binary)
   is generated; `cargo build --manifest-path node/Cargo.toml --release --locked
   --features benchmark` runs against *that* -- compiling every external dependency
   (tokio, rocksdb via bindgen/clang, axum, prometheus, ed25519-dalek, ...) with no real
   application source anywhere in the build context. Because this layer's Docker cache
   key depends only on `Cargo.toml`/`Cargo.lock`, Docker skips it -- and the potentially
   slow rocksdb/bindgen/clang dependency build it performs -- entirely whenever a build
   only changed application source.

   Only then are the real `src/` trees copied in, one `COPY` **immediately followed by
   a `touch`** per crate. Both halves of that pairing turned out to be necessary, not
   just tidy:
   - **The `touch` fixes a real, confirmed bug.** BuildKit's `COPY` preserves each
     file's *original host mtime* instead of stamping "now" (unlike the legacy
     builder). Without the `touch`, a crate's real source -- last edited on the host
     before the build started -- can look *older* to Cargo's mtime-based fingerprinting
     than the dependency-precompile layer's own (necessarily later) stub build of that
     same crate, and Cargo then silently treats the stub artifact as still up to date.
     Caught by actually running the built image: `node --help` printed nothing, because
     the shipped binary was the one-line stub, not the real CLI.
   - **The per-crate COPY+touch pairs are ordered dependencies-before-dependents**
     (`crypto`, `store`, `metrics`, `config`, `network`, `primary`, `worker`, `node`),
     not alphabetically. This is load-bearing too: Docker's layer cache is a strict
     linear chain within one build stage, so once *any* COPY+touch pair is invalidated,
     *every* pair after it in the Dockerfile also reruns -- confirmed empirically with
     an isolated two-file reproduction (an unrelated, byte-identical file copied two
     instructions later still showed as a cache miss, not a hit). With an arbitrary
     order, touching `primary/src/lib.rs` recompiled all 8 crates every time. Ordered
     topologically, it cascades only into `primary`'s actual reverse-dependents
     (`worker`, `node`) -- `crypto`/`store`/`metrics`/`config`/`network` stay genuine
     Docker cache hits and are never touched, confirmed by the build log showing only
     `Compiling primary`/`worker`/`node`, nothing else. The one residual imprecision is
     between same-tier siblings with no dependency relationship (e.g. touching `crypto`
     also spuriously recompiles `store`, purely because `store` is listed after it) --
     always conservative (extra work, never a skipped necessary recompile), and even
     the worst case only ever touches OUR OWN 8 crates, never the external dependency
     graph.

Measured on this machine (macOS Docker Desktop, linux/arm64 VM, 4 build jobs,
`rust:1.95-bookworm`/`debian:bookworm-slim`):

| build | wall time | what happened |
|---|---|---|
| first ever (cold: base image pull + full external-dependency compile) | 3m 47s | dependency-precompile layer builds tokio/rocksdb/axum/... from scratch |
| repeat, zero changes | 1.3s | full cache hit, every layer |
| repeat, real edit to `primary/src/lib.rs` (a comment line) | **10.8s** | only `primary`/`worker`/`node` recompile (verified from the build log); `crypto`/`store`/`metrics`/`config`/`network` stay cache hits |
| repeat, real edit to `entrypoint.sh` only | 1.5s | entire builder stage (Rust compile) is a cache hit; only the runtime stage's own tiny COPY reruns |

The middle two rows are the acceptance proof: a real source-only change to the most
actively-developed crate in this workspace rebuilds in well under 60s, with the
external dependency graph (the expensive part) never touched.

Two more repo-root-adjacent fixes were needed to get a *meaningful* cache-proof number
in the first place, not just a technically-fast one:
- `touch primary/src/lib.rs` with **no content change** turned out not to invalidate
  BuildKit's own `COPY` cache key at all (it hashes content, not mtime) -- so the
  literal command from the task's acceptance bullet is a full cache hit regardless of
  the Dockerfile's design, at 0.7-1.3s, proving nothing about the caching design
  specifically. The number reported above is from an actual one-line content edit,
  which is what "touch primary/src/lib.rs" is really standing in for.
- The very first cold build (3:47) predates the `touch`-after-`COPY` fix above; its
  *timing* is still representative (the fix only changes 8 tiny local crates' own
  compile step, ~10s, negligible next to the ~3.5 minutes the dependency-precompile
  layer takes), but that specific run's own final binary was the stub, caught and fixed
  before any further testing.

### Repo-root changes

Two files outside `docker-bench/` were added, both pure build tooling with zero effect
on any Rust code or on `benchmark/`/fab:

- **`.dockerignore`** (repo root) -- required for the caching design to mean anything.
  This repository accumulates multi-GB `.local-bench-*`/`.db_test_*` run artifacts and a
  large native `target/` at the root; `docker build`'s context must be the repo root
  (the Dockerfile's `COPY primary/Cargo.toml`-style paths need every crate directory as
  a sibling), and without a `.dockerignore` BuildKit has to walk and hash all of that on
  *every* build -- enough on its own to blow the "<60s incremental rebuild" target
  regardless of how the Dockerfile is structured.

## Committee/config generation (`gen.py`)

`gen.py` invokes the **real** `node generate_keys` binary once per node (native build,
`target/release/node`, built on demand with `CARGO_BUILD_JOBS=4` if not already
present) rather than reimplementing ed25519 keypair generation/serialization in Python.
`committee.json`/`parameters.json`'s exact shape was confirmed against a real `node
local-benchmark --nodes 4 --duration 1 --data-dir <tmp>` export (this binary's own
`config::Committee`/`config::Parameters` -- see `node/src/local_benchmark.rs` and
`config/src/lib.rs`), then adapted for a distributed run:

- every authority's addresses are all on the same container IP (`172.28.1.<10+i>`) --
  primary/worker/consensus/metrics all bind `0.0.0.0` internally regardless of what
  committee.json says, so this is exactly analogous to how `fab remote` puts a whole
  authority on one EC2 instance.
- **`mimic_latency_ms` is always explicitly `0`** (present, not `null`/absent). `node
  run` treats an absent/`null` `mimic_latency_ms` as "default to the real
  10-AWS-region `LatencyTable::aws_rtt` matrix, injected **in-process**" (see
  `config::Parameters::mimic_latency_ms`'s doc comment and `node/src/main.rs::run`).
  Since docker-bench injects that same matrix for real via `tc netem` between
  containers, the in-process path must be pinned to an explicit all-zero table or every
  link would be delayed twice. (Confirmed directly: a generated node prints `Mimic
  latency table present but all-zero (PHASE7-PREP-NOTES.md): 4x4 table, no delay
  injected` on startup.)
- one shared `committee.json`/`parameters.json`, mounted read-only into every
  container at `/shared/`; each node's own `key.json` and generated `tc-setup.sh` live
  under its own per-node volume (`data/node-<i>/`, mounted at `/data`), alongside its
  RocksDB stores and primary/worker/client logs once a run starts.
- `--subnet-base A.B` (default `172.28`, matching spec exactly) overrides the first two
  octets of the `/16` if that address space collides with some other docker-compose
  project already using it on this host -- a real thing, not hypothetical: encountered
  exactly this collision (an unrelated `starfish` project's own `172.28.0.0/24`)
  developing docker-bench itself, worked around with `--subnet-base 172.29` for local
  testing. `entrypoint.sh` derives every node's address from `NODE_IP_PREFIX`/
  `NODE_IP_OFFSET` environment variables gen.py writes into the compose file rather
  than hardcoding them, so the override actually takes effect at runtime and not only
  in committee.json/the compose file's own static IPs (an earlier version of this tool
  got exactly that wrong -- the client hung forever dialing an address on the wrong
  subnet -- caught by testing an override end to end, fixed before it shipped).

## Latency injection

`gen.py` bakes in the same 10-region AWS RTT matrix `config::LatencyTable::aws_rtt`
uses (`config/src/lib.rs`'s `RTT_LATENCY_TABLE`, ported verbatim from starfish),
region = node index % 10, one-way delay = RTT/2 -- but applies it with real kernel
`tc netem`, not the in-process simulation. Each node's generated `tc-setup.sh`:

```
tc qdisc add dev eth0 root handle 1: htb default 999
tc class add dev eth0 parent 1: classid 1:999 htb rate 10gbit      # undelayed catch-all
# per peer j:
tc class add dev eth0 parent 1: classid 1:<mid> htb rate 10gbit
tc qdisc add dev eth0 parent 1:<mid> handle <mid>: netem delay <one-way>ms
tc filter add dev eth0 protocol ip parent 1:0 prio 1 u32 match ip dst <peer-ip>/32 flowid 1:<mid>
```

One netem-delay class per **peer container** (not per port): latency is modeled per
authority pair, matching `Committee::addresses_of`'s own doc comment for the in-process
table -- so primary-to-primary, worker-to-worker, and metrics traffic between the same
two nodes all see the same delay. Traffic to any address without its own filter (this
node's own IP -- i.e. its co-located primary<->worker-0 chatter, which is meant to be
LAN-fast -- the docker DNS resolver, the bridge gateway, a metrics scrape's return path)
falls through to the undelayed default class. `entrypoint.sh` runs this script (idempotent:
it tears down any previous `root` qdisc on the interface first) before starting
primary/worker/client. `--no-latency` still generates the script but makes it a no-op,
so the rest of the pipeline is unchanged.

Each node's egress-only delay is one-way; the two nodes' independent one-way delays sum
to the full RTT between them, exactly like the in-process `LatencyTable` convention.

## Client

**No source change was made.** `node/src/main.rs`/`node/Cargo.toml` already ship a
standalone client binary for exactly this purpose: `benchmark_client`
(`node/src/benchmark_client.rs`, a `[[bin]]` requiring the `benchmark` feature) is a
thin CLI wrapper around the same `client::Client` struct `node local-benchmark`
constructs in-process (`target: SocketAddr, size, rate, nodes: Vec<SocketAddr>,
mode`) -- confirmed against `benchmark/benchmark/commands.py::run_client`, which is
exactly what `fab remote`'s own distributed deployment already runs. Its CLI is:

```
benchmark_client <ADDR> --size <bytes> --rate <tx/s> --mode all_zero|random [--nodes <addr>...]
```

`entrypoint.sh` invokes it with `<ADDR>` = this node's own co-located worker-0
transactions address, `--rate` = this node's pre-divided share of `--rate`
(`ceil(rate / nodes)`, computed by `gen.py`, mirroring
`local_benchmark.rs`'s own `rate.div_ceil(load_nodes * workers)`), and `--nodes` = every
node's worker-0 transactions address (the wait-list `Client::wait` blocks on before
sending) -- byte-for-byte the same fields `local_benchmark.rs::spawn_node_workers`
populates, just reached through the standalone binary's CLI instead of an in-process
struct literal.

Because a usable client binary already existed, the task's fallback ("if none exists,
add a `node client` subcommand") was not exercised: no `#[allow]`, no clippy/test
re-run was needed for this deliverable specifically. The Dockerfile builds
`benchmark_client` alongside `node` (`cargo build --manifest-path node/Cargo.toml`,
no `--bin` filter, builds every target the `node` package declares -- both bins).

## Results (`results.py`)

Scrapes every node's **worker** `/metrics` endpoint (`committed_transactions` and the
`transaction_committed_latency{v=...}` histogram gauges live there, not on the primary
-- see `metrics/src/snapshot.rs::read_latency_snapshot`), over the host-published ports
recorded in `data/manifest.json`.

Investigated (so this doesn't have to guess): the exact p50/p90/p99/count/sum
**percentiles** the in-process harness computes are themselves published as ordinary
Prometheus gauges (`transaction_committed_latency{v="p50"}`, in microseconds) --
better than the task anticipated ("if per-tx latency is only computable in-process, say
so"): it is not bucket-interpolated, it's the exact value the in-process summary would
print. The one real caveat: those gauges only refresh every 10s (each node's own
`MetricReporter::REPORT_INTERVAL`), and only the in-process harness can call
`force_report()` to flush the tail before its own final read -- an external HTTP
scraper structurally can't. So a one-shot `results.py` read can be up to ~10s stale;
`--watch` mode (1 Hz, `TIMELINE: sec=<n> committed_total=<n> committed_delta=<n>` --
byte-for-byte the same line format `node local-benchmark --timeline` prints) is the
more faithful way to see a run's actual shape, and is what both `run.sh` and the blip
demo below use.

Committed TPS uses the same formula as `local_benchmark.rs::print_results`: **max
across nodes** of each node's own `committed_transactions` (every node counts
~the same replicated commit stream once its own workers are summed; with this tool's
fixed 1-worker-per-node layout that inner sum is a no-op).

**A real bug, found and fixed**: `committed_transactions` is cumulative *since
container start*, not since whenever `results.py` happens to be invoked. An earlier
version let a one-shot call take `--duration` and report `committed_total / duration`
-- correct only by coincidence when invoked the instant counting starts, and silently
wrong otherwise. Measured concretely: invoking it ~20s into an already-running 4-node,
200 tx/s cluster reported **451 tx/s** (2.3x the true rate), because the numerator
already included everything committed during those first 20s while the denominator
assumed counting had just begun. Fixed by making `--watch` self-baseline from its own
first and last samples (`(last_total - first_total) / (last_elapsed - first_elapsed)`,
correct regardless of how long the cluster had already been running) and by dropping
the misleading one-shot shortcut entirely -- a plain `results.py` call now prints only
point-in-time cumulative counters, explicitly labeled as such, never a derived rate.
Re-measured with the fix, same 4-node/200 tx/s cluster: **203 tx/s** over an 11s watch
window -- both `run.sh` and the blip demo below use `--watch` for exactly this reason.

## Blip / link disruption (`blip.sh`)

```
blip.sh <i> <j> <seconds> drop|cut
blip.sh <i> all <seconds> drop|cut
```

Host-side script; `docker exec`s into container `i` and inserts iptables rules against
peer `j`'s (or every peer's, for `all`) container IP, sleeps, then removes them
(idempotent: cleanup runs from an `EXIT`/`INT`/`TERM` trap, so Ctrl-C mid-blip still
restores connectivity).

- **`drop`**: `iptables -I INPUT -s <peer-ip> -j DROP` + `-I OUTPUT -d <peer-ip> -j
  DROP`. Packets are silently discarded -- no RST, no ICMP. *Pause* semantics: an
  open TCP connection gets no explicit teardown signal, just stalls; if the blip ends
  before either side's retransmit/keepalive gives up, the same connection resumes with
  no reconnect and no lost socket state.
- **`cut`**: `iptables -I INPUT -s <peer-ip> -j REJECT --reject-with tcp-reset` (+
  `OUTPUT`). An immediate RST tears down any open connection between the two nodes
  right away -- exercises the disconnect/reconnect path (new TCP handshake, the
  `network` crate's own retry/backoff) instead of a silent pause.

macOS still ships bash 3.2 as `/bin/bash` (GPLv3 avoidance); pre-4.4 bash treats
`"${arr[@]}"` on a genuinely empty array as an unbound-variable error under `set -u`.
`blip.sh` avoids ever hitting that path (an explicit check rejects the one input that
could make its peer-IP array empty; the DROP-vs-REJECT branch is a plain `if`, not a
shared "extra args" array expanded at every call site) -- verified directly against
`/bin/bash` on this machine, not just whatever `bash` happens to resolve to on `$PATH`.

## Linux-host notes

This is where docker-bench is meant to actually run. On a real Linux docker host
(`cap_add: NET_ADMIN` + the kernel's own native `tc`/netem/htb/iptables, no VM layer in
between):

- `tc qdisc`/`class`/`filter` and `iptables` behave exactly as documented above with no
  caveats -- no nested-virtualization networking quirks to work around.
- BuildKit cache mounts persist across builds on that host indefinitely (there is no
  ephemeral-runner cache-eviction concern here -- this tool is designed for a single
  persistent dev/CI box, per the caching section above), so the incremental-rebuild
  timings measured above should if anything be a ceiling, not a floor.
- `docker compose`'s default bridge driver on Linux gives real kernel `veth` pairs;
  `tc` on each container's `eth0` shapes real egress traffic, not something running
  through an extra virtualization hop.

## What was / wasn't verifiable on macOS

Developed on macOS Docker Desktop (Docker Desktop 4.64, linux/arm64 VM, kernel
6.12.72-linuxkit). Unlike the "verify what you can, report what can't be exercised"
fallback this deliverable was scoped for, **`tc`'s `netem`/`htb` qdiscs both loaded
successfully in this VM's kernel** (checked directly: `tc qdisc add ... netem delay
50ms` / `... htb default 999` both against a throwaway `--cap-add=NET_ADMIN`
container, no error) -- so the full stack, including real latency injection, was
exercised end to end, not just verified statically:

- **Build/caching**: both timings in the table above, plus the two bugs the process of
  actually running the built image surfaced (the stub-binary mtime bug; the
  cache-cascade-vs-topological-order distinction) -- neither would have been visible
  from reading the Dockerfile alone.
- **`gen.py`**: keys via the real `node generate_keys`; `committee.json`/
  `parameters.json` schema cross-checked against a real `node local-benchmark --nodes 4
  --duration 1` export; a real `node run` parsing every generated file without error
  (confirmed `Mimic latency table present but all-zero`, i.e. `mimic_latency_ms: 0` is
  wired correctly); generated `docker-compose.yml` validated with `docker compose
  config`; the `--subnet-base` override, including the entrypoint.sh propagation bug
  it initially exposed (see "Committee/config generation" above).
- **Latency injection**: brought up a real 4-node cluster and `docker exec ... ping`ed
  between several pairs. Measured RTTs matched `RTT_LATENCY_TABLE` within ~2ms
  (virtualization overhead), e.g. node0<->node1 (region 0<->1, table RTT 14ms):
  measured ~16ms; node0<->node2 (region 0<->2, table RTT 104ms): measured ~106ms;
  node0<->node3 (region 0<->3, table RTT 112ms): measured ~114ms; node1<->node2
  (region 1<->2, table RTT 106ms): measured ~108ms.
- **End-to-end run**: `./run.sh --nodes 4 --rate 200 --duration 60 --protocol vantage`
  (and shorter variants) ran unmodified, start to finish, no manual intervention:
  gen -> build -> up -> wait (containers answered instantly once up) -> a full
  1 Hz `TIMELINE:` series -> self-baselined summary -> down. Reported TPS tracked the
  requested rate closely (203 tx/s measured against a 200 tx/s target; 155 against 150
  in a separate run) -- not just "the pipeline runs", the reported number is right.
- **`blip.sh`**: `blip.sh 0 1 5 drop` mid-run produced a clean dip and recovery in the
  live timeline --
  `committed_delta` fell from a steady ~200/s to `15, 0, 0, 26, 0` for the 5s window,
  then a catch-up burst (`248, 272, 1170`) before settling back to ~200/s. Verified the
  iptables rules were actually removed afterward (`iptables -L INPUT` on the target
  container showed no leftover DROP rule).
- **`results.py`**: the Prometheus-text parser against a synthetic `/metrics` sample,
  and (see "Results" above) a real, confirmed-wrong TPS calculation caught by actually
  reading the number it produced against a known input rate, not just by the script
  running without error.

Net: every deliverable was exercised against a real, running 4-node cluster on this
machine, not only reviewed statically. The Linux-host notes above describe what should
be *more* robust there (no VM layer, persistent BuildKit cache across runs), not
functionality that was untestable here.
